No Spring dependency in domain/application/security/persistence. One executable jar, no provider SDK in runtime.

## Executable
- file-storage-runtime is a Spring Boot MVC shell; no component scanning of internal controllers. Default API role, explicit API/TRANSFER/WORKER/COMBINED role names. These are startup role markers only: no transfer/worker behavior. Only /health/live (200) and /health/ready (503 until actual dependencies and authority are verified) are registered. The isolated process enforces 127.0.0.1 binding and rejects other addresses and invalid roles. No production enable switch.
- RuntimeComposition explicitly delegates migration to StorageMigrations and creates SecuredFiles with JdbcTransactions, trusted verifier, bindings/membership/entitlement/grants, clock and explicit TTL/lease. No automatic DB connection/migration, permissive authority or secret default. No runtime API access without separate wiring and approval.
- Build with make ci; executable jar under backend/file-storage-runtime/target. Run java -jar file-storage-runtime-0.0.1-SNAPSHOT.jar --server.port=8080 --fs.role=API locally. Do not deploy; no real readiness or authority configured.

## Proposed v1 contract
See contracts/openapi/file-storage-v1.yaml. FileRoutes is registered only by isolated test configuration; every operation invokes SecuredFiles. POST /v1/uploads initiates metadata only (200 on creation or replay), GET /v1/uploads/{sessionId}, GET /v1/files/{fileId}. Tenant header is requested scope, never identity. Authorization bearer goes to trusted verifier; no actor/consumer supplied by client. Idempotency-Key header required for initiation. X-Correlation-Id optional; X-Request-Id fresh; safe logical FileReference and explicit scalar DTOs. No provider data or byte transport. Invalid request 400, authentication 401, denied 403, missing 404, conflict/in progress 409, no placement/unavailable 503. Neutral errors and no-store for handled responses. Container-level malformed requests/unknown routes, request body bounds, header multiplicity, logging, full schema verification, control-plane DTOs and production error mapping remain future slices.

## FS-300A continuation — HTTP boundary refinement (issue #30, quality #65)
PR #64 accepted and squash merged at 6ed88c1e5cc4a551f39103a491e1472514e4d666; CI 43691154932 passed 125 tests (56 PostgreSQL, 13 MinIO, 12 OSS SDK, 4 embedded HTTP, 40 other), zero failures/errors/skips. Owner authorized continuation and requested cleaner code/structure. This slice is deliberately limited to the isolated metadata HTTP boundary.

- Package runtime.http separates thin FileRoutes, FileDtos, ApiRequest, ApiResponses, ApiErrors, ApiAdmissionFilter and ApiHttpConfiguration. RuntimeRole expresses role responsibilities; metadata routes explicitly require API or COMBINED. Default executable still health-only and loopback, readiness 503; no production enable switch or live authority.
- Admission rejects duplicate/comma-joined singleton headers (Authorization, tenant, correlation, idempotency, content type/encoding). Reject nonidentity content encoding, fixed or chunked metadata POST body above 16 KiB before MVC deserialization or application writes. Bounded synchronous buffer only for metadata; never use this filter for future byte transfer routes. This is an isolated engineering ceiling, not a production file-size/transport policy. Container header/request limits, connection timeouts, concurrency/rate limits, slow-client defense and logging remain deployment/security gates.
- Common response envelope: neutral status/code, correlation/request IDs, no-store, Bearer challenge on authentication failure. 413 oversized, 415 unsupported media/encoding, 406 unacceptable representation, 405 unsupported method with Allow and 404 unknown path in explicitly composed API. No arbitrary exception messages. Servlet/container-level failures before the filter, error dispatch and full production logging/security are separate work.
- Existing v1 success shape and FileReference unchanged; no new schema or dependency. Four additional embedded HTTP tests target role gating, fixed/chunked oversized bodies, ambiguous headers/encoding, malformed/unsupported/unknown HTTP errors and no writes. Exact-head CI required; no public exposure or production DB migration.
