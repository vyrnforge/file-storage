# FS-310A9 historical accounting manifest and restricted execution

Status: implementation candidate; CI and owner review pending. Refs #13 #16 #33 #35 #36.

V19 adds immutable manifest headers, per-session entries, and independent review. A current independently reviewed quota activation is required for a non-integrated tenant. The manifest retains exact metadata inputs (logical IDs, private internal placement IDs, session/version/file state, request bytes, claim and matching integrity evidence, existing ledger pins/status); untracked versions are enumerated separately. Candidate RESERVED/CHARGED/RELEASED/UNRESOLVED/ALREADY_ACCOUNTED are estimates, not provider truth or executable instructions. A completed session requires AVAILABLE version, matching durable integrity evidence and CLEAN scan evidence with matching bytes/digest for a candidate charge. Release candidates require failed version, terminal recovery evidence and no claimed write. Claimed terminal failure or inconsistent existing ledger evidence remains unresolved. The manifest does not change quota, accounting, lifecycle, provider data or integration.

## Execution boundary

Two explicit login-role mappings associate a tenant, trusted actor and CAPTURE or REVIEW capability. Owner-controlled isolated provisioning grants schema USAGE and only the appropriate SECURITY DEFINER command and scoped read function. Commands use session_user (not supplied actor or SET ROLE), fixed search_path and UTC, explicit tenant equality, and revoked PUBLIC execution. No production role or automatic grants are created. No direct source-table or manifest-table grants are required. The migration owner remains privileged; trusted role provisioning and credential lifecycle require separate review. This is a restricted historical manifest execution foundation, not full application runtime role conversion or RLS. A separate disposable non-owner initiation login exercises the existing integrated quota/Kernel transaction with explicit table/column/function grants, replay, capacity and outbox rollback; it cannot change quota policy, enablement, delete ledger or inspect manifest principals. V4 FOR SHARE needs UPDATE(endpoint) on the backend row; the existing physical-identity trigger rejects changes. Kernel v0.3.2 event intent replay requires UPDATE(event_id) because its exact-content upsert assigns the same event ID; this is a trusted writer column privilege, not permission to mutate payload/delivery state or delete events. Direct guarded ledger inserts and epoch writes remain trusted application-writer capabilities. Completion/recovery still run in existing owner-fixture tests; production write-role hardening and tenant-level RLS remain gated. Database owner and superuser are outside the threat boundary. The manifest/review rows are the durable evidence; Kernel audit/outbox integration for these commands is deferred.

## Snapshot and review

Capture and review use READ COMMITTED and SHARE table locks on all enumerated source tables; this intentionally coarse isolated rehearsal fence also covers non-integrated writers. Lock timeout is two seconds per lock; callers must bound the entire statement/transaction. Capture is capped at 1000 sessions and versions, rejects an integrated tenant, binds the exact current reviewed policy revision and its evidence TTL, and commits header/entries atomically. Review requires a different mapped actor, same revision, non-expired evidence and exact set comparison against current entries/untracked versions. Same-ID identical command replay returns the prior immutable result; replay never refreshes evidence or grants execution. A bounded per-manifest advisory lock serializes duplicate capture/review commands; unrelated source contention can still conflict and require retry. A transactional per-tenant source epoch is created on first capture; source row triggers advance it on all relevant committed changes, including change-and-revert. Review rejects epoch mismatch in addition to exact row comparison; scoped reads mark expired or changed evidence non-current. Rolled-back changes roll back the epoch. Owner-level TRUNCATE, disabled triggers, restores and direct epoch edits are outside the restricted-role boundary. Post-review changes make evidence stale; no execution exists. Any future execution would require independently approved fresh transactional revalidation. Global locks and source-epoch trigger overhead are unsuitable for production throughput without load and design review. Epoch updates are restricted to previously captured tenants; trigger lookups still occur on all source writes. New contention paths can abort source transactions rather than compromise evidence.
