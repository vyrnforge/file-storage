## Authority and contract

JdbcPolicyControl composes existing JdbcConfiguration with an injected trusted PolicyAuthority. Every publish, rollback, active/historical detail and history request checks exact actor + tenant/application/purpose. Before publication or rollback and returning rule details, authorize **every** location, including disabled or nonwinning rules. Empty location set checks scope only. Authority failures deny without provider details. The port must be wired to verified IAM identity and authoritative server-side entitlements, not request flags; live integration and revocation/transaction policy remain gated. A history list returns only sealed revision numbers after scope authorization. Existing JdbcConfiguration remains trusted low-level persistence, not a public authorization surface.

- Publish requires nonempty distinct logical locations, nonnegative priorities, at most 100 rules, exact expected active revision; 0 for initial. Scope consumer/purpose limited to 128 characters. Existing CAS, location existence, backend locks and actual StorageModel.select decide valid publication. The unique minimum-priority rule must be eligible and active; no fallback if it is ineligible, ambiguous or inactive. Lower-priority rules are not automatic failover.
- Reads use fresh committed PostgreSQL snapshots; active detail resolves pointer and immutable rules in one statement. Bounded history keyset pages (1–100, before=0 first page), and logical-only views. No process-local cache or provider target/credential data. Oversized historical policies fail closed rather than truncate. No list-all-tenant or cross-scope administration.
- Rollback copies an earlier sealed revision into a new publication, rechecks all current permissions and the current active backend winner, CAS against expected active revision, no pointer rewind. Existing file/session/operation references retain pinned identities. Required policy.published event/audit records retain tenant, logical scope, previous/new revision and rollbackSourceRevision for rollback. No raw credentials or object keys.
- Authority is checked before DB CAS; live authority changes between check and commit require a production revocation/fencing policy before exposure. No claim of atomic external IAM authorization. Existing trusted persistence methods and DB roles must not be exposed directly. No new dependency, migration or adapter changes.
