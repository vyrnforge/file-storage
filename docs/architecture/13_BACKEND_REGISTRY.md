# FS-210A — Backend and location registry

Owner authorized [#27](https://github.com/vyrnforge/file-storage/issues/27) after PR #60 merged at 972e091004725f1d3eef11d550fa773e4897545e. #20/#22 existing CAS and atomic intents reused. #26 stays open for actual OSS staging and #14 legacy evidence. This is a trusted internal foundation, not an admin API or production secret manager.

## Commands and reads
- registerBackend(actor, correlation, Target, CredentialRef): new UUIDv7 identity + unvalidated DRAFT revision 1 in one Kernel transaction. HTTPS root endpoint only, normalize host/default port/trailing slash, bounded region and opaque reference; no provider I/O. Compiled S3/OSS only. Does not authorize or prove endpoint/network safety, adapter capabilities or credentials.
- registerLocation(actor, correlation, backend, bucket, prefix): UUIDv7 identity; conservative bucket syntax and normalized namespace, no traversal-like segments/control/backslash, prefix bound leaves space for service key. Initial location set only: reject after any validation or non-DRAFT history. This avoids adding an unvalidated location to an active backend; revision-aware later location admission belongs to #28. For now a separate backend with disjoint location is an option. Lock storage_location in SHARE ROW EXCLUSIVE mode then backend identity row; reject same normalized known endpoint/bucket overlapping namespaces (including empty prefix). Different DNS aliases, provider endpoints/CNAME and real physical equivalence cannot be proved here; #28 must verify canonical provider identity and isolation. V1 physical identity update triggers retained, no new migration; raw privileged DB writes can bypass command checks, restrict roles later.
- reviseCredential(actor, correlation, backend, expectedLatest, nextRef): parent lock, exact latest CAS, append new DRAFT revision latest+1; never change active pointer, old reference or historical physical identity. Rollback is a new candidate referencing a prior still-valid immutable secret version, not a rewind. Activation remains JdbcConfiguration and requires trusted exact revision validation. No admin idempotency yet. Failed required intent rolls back all writes.
- backends(after,limit), locations(backend,after,limit), history(backend,before,limit), active(backend): bounded fresh committed reads, 1–100 rows; safe logical IDs/provider/status/revisions only, no private endpoint/bucket/prefix/reference. No local config cache: each new read uses authoritative DB, so separate instances see committed revisions without invalidation protocol; already-acquired snapshots/clients remain subject to future lifetime/revocation policy. Keyset pages are not a point-in-time snapshot. Admin-authorized private detail DTOs/routes later.

## Credential resolution
Application CredentialResolver<C extends AutoCloseable> port receives only exact persisted reference to immutable secret version or workload-identity binding. Concrete implementation must not resolve mutable aliases to latest or fallback; no raw secret in DB, events, config output or source. Reference syntax is not evidence of secret-store authorization or immutability. #16 owner selects managed secret store/workload identity and rotation/revocation/lifetime policy; no production provider chosen. 
JdbcRegistry.resolveExisting(backend,revision,location,resolver) reads exact validated ACTIVE/DRAINING pin and checks location belongs to backend; unknown, draft, retired or mismatched pin NOT_FOUND. External resolution after DB transaction; null/unavailable/revoked resolver DENIED, no fallback. Caller must already have authorized session/file and exact pin. Returned internal Resolved handle owns credential lease, redacted toString; never serialize or expose. Caller closes; no cache. A revocation after lookup cannot recall acquired credentials or bytes; actual short-lived credentials/client lifetime and in-flight policy remain #16/#28/#43. Resolver not used for draft validation here; #28 trusted validator separate. Synthetic tests exercise resolution/revocation only, not actual secret-store or provider reads.

## Atomic intents
Kernel JdbcReliabilityTransaction 0.3.2, read committed; three version-1 global events and audit records: file-storage.backend.registered, file-storage.location.registered, file-storage.backend.credential-revised. Minimal logical resource ID/provider/revision/backend ID; no private targets, buckets, prefixes or reference. Trusted actor/correlation via existing MutationIntents. No broker delivery claim.

## Acceptance

R02 normalize known endpoint, deny overlap/invalid namespace and late location admission; no provider calls. Concurrent overlapping admissions serialize.
R03 append revision CAS, fresh active/history across registry instances, original pin and old reference retained after simulated activation, exact resolution and lease close, draft/mismatch denial and synthetic revocation without fallback; rollback is new draft.
R04 competing credential revisions one winner; forced outbox failure rolls back registry and audit. Existing regression suite and dependency boundaries.
R05 actual secret manager and workload identity decision, concrete resolution and real rotation/revocation/provider reads remain #16/#28/#43; no closure on internal tests alone unless owner explicitly accepts bounded scope and tracks deferred evidence. No public admin runtime, actual credentials, network calls or deployment.
