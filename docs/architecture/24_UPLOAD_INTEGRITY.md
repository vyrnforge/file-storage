## First completion slice
V6 creates fs.upload_integrity_verification, immutable first expected SHA-256 request keyed by the existing unique upload transfer session, and monotonic matching evidence (verified_at, observed_size and observed_sha256). No provider secrets, raw handle, byte content or external URI. The existing upload and file version states remain INITIATED/PENDING until a later durable lifecycle transition and scan gate; evidence alone cannot authorize download. No MIME inference, malware verdict, cleanup, reissue, worker scheduler, public completion route or AVAILABLE state in this slice. The expected digest is provided by the authenticated initiating caller at verification request time, not an independently trusted origin or pre-upload manifest. It is immutable thereafter; changing a mistaken first digest requires a future reconciliation policy.

UploadIntegrityVerification is a trusted internal synchronous orchestration port. Reuses SecuredFiles.authorizeUpload (explicit UPLOAD_TRANSFER grant, current identity/membership/entitlement, exact initiating caller, pending session/version and expiry); no new implicit read permission. JdbcUploadVerification reuses exact session/resource locks and same-DB grant fence in JdbcUploadTransfers, requires a matching already claimed handle, stores request and intent atomically, returns an internal pin for read-only verification. The claimed handle is not proof of transfer success. Session expiry, not the consumed handle's shorter expiry, bounds verification. Provider read uses exact backend revision/location/object key; no latest fallback, no DB transaction during provider I/O. HEAD requires exact declared size; GET reads bounded buffer to EOF, computes SHA-256 of actual bytes and compares expected digest and optional provider SHA-256 (never ETag). Size/hash mismatch, missing data, timeout or failure leaves only the durable request, not successful evidence; retries of same request can reconcile a late/uncertain staged write without overwriting or reissuing. Close stream and provider/credential lease before persisting evidence; cleanup failure prevents a success record. Reauthenticate before final evidence CAS; recheck same-DB grant, pending resource, claim, pin and session expiry. Atomic required audit/outbox record on first matching commit; same-hash replay returns original evidence without provider I/O or duplicate intents. Concurrent read-only verifications may duplicate reads but serialize evidence commit on session; no worker lease or retry scheduler yet. Only logical file/session/version in events. Explicit bounded max size, concurrency and cooperative deadline; provider transport deadlines are separately configured. Internal repository trusts verifier measurements, never expose its methods directly as API routes.

Unversioned create-only storage profile and controlled service writes assumed. Out-of-band mutation/deletion after a read, external IAM revocation race, cross-process resource limits and production transport deadlines remain deployment/security gates. SHA-256 match is point-in-time integrity, not continuing availability or scanner clearance. Next: durable VERIFYING state/scan job, trusted scanner verdict bound to exact content, lifecycle CAS and safe failure/expiry/reconciliation, #32 content/scan policy and #33 quota; no clean verdict inferred. Actual OSS staging #26 and live provider credentials #16/#27/#28 remain deferred.
