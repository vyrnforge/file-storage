## Authority and storage
- DurableUploadAuthority composes existing SecuredFiles and JdbcUploadTransfers. Internal issuance takes bearer, requested tenant, logical session and correlation; no public issue route or client placement input. SecuredFiles authenticates token using existing trust/verifier, resolves authoritative USER binding, membership, module entitlement, explicit UPLOAD_TRANSFER action and current resource grant. FileApplication.authorizeUpload requires exact initiating caller (tenant/actor/application), active file, pending version, initiated/unexpired session and grant. Read/initiate grants do not imply transfer. Grant administration is not implemented; fixture uses real JdbcGrants with synthetic identity. Download claims always deny: current schema has only pending versions, no verified availability; #31/#35 own that lifecycle.
- Generate 256-bit SecureRandom handle, canonical base64url 43 chars; persist SHA-256 of decoded bytes only. One initial handle per session (unique session ID), no overwrite or reissue even after expiry/claim; explicit conservative first-attempt profile, not an approved retry policy. Issuance returns raw handle once internally; no logs/DTO projection. TTL explicit, bounded <=1h, floored to DB microseconds, never later than session expiry. Lost response/expired/uncertain attempts require #31 reconciliation/reissue decision. No automatic retry.
- V5 row records immutable tenant, initiating actor/app, session, file/version, exact backend revision/location/key and expected length; FKs to existing session, version, location/backend revision. Trigger rejects binding changes and resetting or changing an existing claim. Repository resolves all fields from locked current session/resource, not caller; activation/drain preserve pin, retired/draft/invalid revision denies. Read-committed transactions use Kernel JDBC reliability; session FOR UPDATE serializes competing issuance/claim, resource/revision FOR SHARE locks. Hash lookup alone never authorizes. Claim first reauthenticates current identity/grant outside claim transaction, then rechecks all resource/pin fields and expiry inside transaction; atomic UPDATE ... claimed_at IS NULL returning expiry. Claim commits before provider resolution/bytes. Required audit/outbox intents for successful issuance and claim contain logical file/session/version only, not hash/token/locator/provider credential. Intent failure rolls back; no success on uncertain transaction outcome.
- The repository additionally rechecks and locks a current matching durable UPLOAD_TRANSFER grant FOR SHARE during issue/claim. A committed revocation before the check denies; a concurrent revocation of the authorizing row waits until claim commit. This increment requires a durable local grant even if a different external Grants port is configured. External identity/membership/entitlement revocation between trusted authorization and local claim commit remains a check-time race; no distributed linearizable revocation or in-flight cancellation guarantee. Live IAM #17–#19, production grant administration, transport/TTL/reissue/retention decisions #16/#31/#43 remain gates. Synthetic identity is not live IAM. Privileged database administrators can bypass triggers; production roles and retention policy not selected. Handle lookup/claim query timeout explicit; pool/network limits and clocks must be approved for deployment. No provider I/O in transaction, no credential resolution in this increment.
