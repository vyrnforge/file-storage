## Explicit drain
JdbcConfiguration.drainBackend(actor, correlation, backend, expectedActiveRevision) locks the backend identity and changes only the exact ACTIVE revision to DRAINING. Unknown backend NOT_FOUND; nonpositive revision INVALID; stale, already drained or draft revision CONFLICT. Existing V2 trigger enforces allowed transition. Successful change commits one global audit and one event intent (file-storage.backend.drained, logical backend ID and revision only) on the same Kernel 0.3.2 transaction. Required intent failure rolls back status. No provider I/O, no credential revocation and no new schema.
- New placement snapshots cannot select a drained backend; a policy still pointing there fails NO_PLACEMENT, without fallback. Switch policy to a validated replacement before drain for new-write continuity. Existing authorized sessions retain pins; resolveExisting accepts validated DRAINING. Already acquired repeatable-read snapshots can finish with their historical pins; drain is not a hard cancellation barrier.
- Existing activation CAS disallows reactivation after explicit drain with no active revision. Explicit drain is one-way in this increment; credential rotation before drain can activate a new revision. Reopening drained backend requires a separate reviewed contract; do not silently rewind. Concurrent activation and drain of the same active revision have one winner.
- Internal commands require trusted actor/correlation, not an admin authorization boundary. Actual provider operations and in-flight revocation behavior remain gated.
