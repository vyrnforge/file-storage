## Explicit drain
JdbcConfiguration.drainBackend(actor, correlation, backend, expectedActiveRevision) locks the backend identity and changes only the exact ACTIVE revision to DRAINING. Unknown backend NOT_FOUND; nonpositive revision INVALID; stale, already drained or draft revision CONFLICT. Existing V2 trigger enforces allowed transition. Successful change commits one global audit and one event intent (file-storage.backend.drained, logical backend ID and revision only) on the same Kernel 0.3.2 transaction. Required intent failure rolls back status. No provider I/O, no credential revocation; drain itself introduces no schema change.
- New placement snapshots cannot select a drained backend; a policy still pointing there fails NO_PLACEMENT, without fallback. Switch policy to a validated replacement before drain for new-write continuity. Existing authorized sessions retain pins; resolveExisting accepts validated DRAINING. Already acquired repeatable-read snapshots can finish with their historical pins; drain is not a hard cancellation barrier.
- Existing activation CAS disallows reactivation after explicit drain with no active revision. Explicit drain is one-way in this increment; credential rotation before drain can activate a new revision. Reopening drained backend requires a separate reviewed contract; do not silently rewind. Concurrent activation and drain of the same active revision have one winner.
- Internal commands require trusted actor/correlation, not an admin authorization boundary. Actual provider operations and in-flight revocation behavior remain gated.

## Trusted draft validation boundary
JdbcRegistry.validateDraft reads an exact unvalidated DRAFT with 1–100 locations under the backend identity lock, then releases the transaction. The deployment-supplied approved target set must match the entire canonical Target. Literal IPs, single-label hosts, localhost suffix, metadata.google.internal and CNAME are denied before the trusted BackendValidator is invoked. This is syntactic admission, not DNS/SSRF protection: the concrete deployment validator must independently constrain resolved addresses, TLS hostname, redirects, actual connection egress, credential authority and bounded deadlines/concurrency. No concrete provider validator or secret manager is installed here.
- The trusted port receives the exact immutable credential reference and location set; returns checks keyed by exact backend, revision and every location ID. All ten checks must pass (TLS, endpoint egress, exact credential, provider identity, required capabilities, private bucket, encryption, unversioned profile, least privilege, canary cleanup). No arbitrary admin assertion, raw provider error or materialized credential in reports. Candidate/report toString redacted. The trusted validator is responsible for actual provider evidence; a synthetic report proves only the orchestration contract.
- No provider I/O inside a metadata transaction. Re-read and compare the entire candidate under the parent lock before setting validated_revision. Concurrent location admission, validation or status changes cannot silently approve an altered candidate. Required audit/event intents (file-storage.backend.validated; revision and location count only) commit together. Activation still uses existing exact revision CAS. The current schema records validated_revision and audit/event, not a durable full evidence artifact or expiry; concrete evidence provenance/lifetime and approved policy remain #16/#28. Existing privileged SQL fixtures are not a production validation path.

## Guarded retirement
V4 preserves V1–V3 history and strengthens the existing backend revision trigger. JdbcConfiguration.retireBackend locks the parent, checks blockers, CAS transitions exact DRAINING to RETIRED, and atomically records file-storage.backend.retired (logical ID/revision). V4 independently checks reference guards in a read-committed retirement transaction; updates the parent row without changing its physical identity to create an MVCC fence. No deletion of bytes, credentials or historical metadata.
- Conservative backend-wide blockers: any ACTIVE revision; any file_version, upload_session or storage_operation at the backend (including claimed, dead or terminal retained jobs); any current policy rule targeting the backend. Historical inactive policies are retained, not blockers. This deliberately prevents retiring even an unused old credential revision while the backend is active or referenced, since version/job records pin locations, not credential revisions. Cleanup/retention and more granular retirement are future work.
- V4 reference admission triggers lock the same parent FOR SHARE before file_version and upload_session insert or location/pin changes. Upload sessions must reference exact ACTIVE/DRAINING revision. A repeatable-read transaction with a pre-retirement snapshot fails on the changed parent version instead of attaching a stale reference. If reference admission wins the lock first, retirement observes committed references and blocks. Storage operations have a mandatory version/location FK, so a job cannot arise without a blocking version. Policy pointer admission locks parent identities and rejects fully retired backends; existing active rules block retirement. Database owners can bypass triggers; production role hardening remains gated.
- V4 applied only to disposable verification DB, not production. No hard cancellation/revocation of acquired client handles. Explicit drain remains one-way. Retirement is intentionally conservative, not a guarantee of provider resource cleanup.
